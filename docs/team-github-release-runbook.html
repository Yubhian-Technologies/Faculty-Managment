01 — Context

The problem, concretely

This isn't hypothetical. The repo already shows the failure mode: production has a commit whose message is literally "tabs are hidden except hiring and management" — someone went file-by-file commenting out nav entries and gating specific pages to control what's visible in production. That works exactly once. The next time main moves forward, someone has to redo that reconciliation by hand, because production's history has diverged into its own branch of edits rather than staying a clean mirror of main.

Two structural gaps are causing this, and both get worse as team count grows:

  • No release mechanism below "whole app." The only way to hide an unfinished section from production today is to physically remove or comment out the code that renders it, on a branch that then has to be kept in sync by hand.
  • No ownership boundaries. Shared files — navConfig.ts, types/core.ts, proxy.ts, the shared UI kit — get touched by every team, on every feature, so they're the highest-conflict surface in the repo and nobody is accountable for their shape.

Everything below fixes those two gaps directly: §3 replaces branch-level hiding with a config flag, and §4 assigns real owners to the shared surfaces.

02 — Git

Branching model

Trunk-based, not GitFlow, and not long-lived personal branches. One integration line, short-lived branches feeding it, and a production line that only ever fast-forwards from main — it never accumulates commits of its own.

feature/*
main
production
branch: feat/leave-balance-fix
flag: hiring → live
flag: budget → beta

Solid line = real commit history. Dashed line = production tracking main via fast-forward, not its own commits. Each release is a flag flip at a point in time, not a branch.

Branch roles

BranchPurposeWho commits directly
mainAlways integrated, always deployable to staging. Every merged PR lands here first.Nobody — PR only
productionDeploy target. Fast-forwarded from main at release time. Carries no commits main doesn't have.Nobody — fast-forward only, via release PR/tag
feat/<section>-<desc>One ticket, one branch, off main. Merged and deleted within days.The engineer working the ticket
fix/<section>-<desc>Same lifecycle as feat/*, for bug fixes.The engineer working the fix

You already use this naming pattern in places — feat/speed-insights, fix/disable-lint-during-build are good examples already in the repo. The gap isn't the convention, it's that it isn't applied consistently, and branches aren't deleted after merge (see §8).

Rules

  • No direct pushes to main or production — PR required, enforced by branch protection (§5).
  • Branch from main, always. Never branch from another feature branch or from production.
  • Keep feature branches short-lived — rebase or merge main in daily if the ticket runs past 2–3 days, so divergence never compounds.
  • Delete the branch on merge (GitHub can do this automatically on PR merge — turn that setting on).

03 — Release mechanism

Section gating: flags, not branches

The fix for "release one section at a time" is a config flag that every code path reads, not a branch that physically excludes code. main and production build from the same source; what differs is which sections are switched on.

You already have this pattern in the codebase — ROLE_SCOPE in src/types/core.ts is described as "the single source of truth... old duplicated literals now all import this." Section flags are the same idea, applied to release state instead of role scope.

Proposed source of truth

// src/config/sections.ts
export type SectionKey =
  | "hiring" | "budget" | "leave" | "payroll" | "teaching"; // adjust to your real 5

export type SectionState = "off" | "beta" | "live";

// beta = visible to SUPER_ADMIN/section QA roles only, for staging soak time.
// off  = invisible to everyone in this environment.
export const SECTION_STATE: Record<SectionKey, SectionState> = {
  hiring:   "live",
  budget:   "beta",
  leave:    "off",
  payroll:  "off",
  teaching: "off",
};

export function isSectionVisible(section: SectionKey, role: UserRole): boolean {
  const state = SECTION_STATE[section];
  if (state === "live") return true;
  if (state === "beta") return role === "SUPER_ADMIN"; // widen as your QA process needs
  return false;
}

Start as a static map read from env (one deploy per flag change is fine at 5 sections); move it to Firestore later only if you need to flip flags without a redeploy.

This is exactly the reconciliation work done by hand in this session's production merge — the flag makes it a one-line change instead of a conflict-resolution exercise, every single release.

StateMeaning

05 — Mechanics

GitHub mechanics

Branch protection

  • main: require PR + 1 approval, require status checks (typecheck + build) to pass, dismiss stale approvals on new commits, no force-push.
  • production: same, plus restrict who can merge into it to release leads only.

Every PR

  • Title format: [section] short description — e.g. [budget] fix fund allocation rounding.
  • Body answers: which section, which flag state it ships under, how it was tested.
  • CI green before merge — you already have working build/typecheck commands (via the Node 24 direct-binary workaround noted in the repo), wire them into a GitHub Actions workflow if one doesn't exist yet.

Project tracking

One GitHub Project board, with a Section field (Hiring / Budget / Leave / Payroll / Teaching / Platform) rather than one board per team — that way a section lead can filter to their column regardless of which team picked up the ticket, and cross-section dependencies stay visible in one place.

06 — Process

Release checklist

Before a section's flag moves from beta to live in production:

  1. Every API route the section touches has a requireCollegeMember/requireRole/requireLocationMember guard — no open endpoints.
  2. Every nav entry the section adds resolves to a real, data-backed page — no placeholder "coming soon" screens left reachable (this repo just shipped one of these live by accident on /panel/teaching; make this check explicit so it doesn't happen again).
  3. Writes create the matching AuditLog entry and AppNotifications, per the unions in types/core.ts.
  4. next build and typecheck both pass clean on the exact commit being released.
  5. Section lead signs off in the release PR description; Platform team reviews any changes to shared files it touched.
  6. Flip SECTION_STATE.<section> to "live", merge, fast-forward production.

07 — Planning

Planning cadence

AGENTS.md is already a real architecture doc — most projects this size don't have one. Keep it living: every section owner updates its relevant paragraph when their module's shape changes, not just when someone happens to notice it's stale.

  • Weekly section-lead sync (15 min): each of the five section leads states flag state, what's blocking a state change, and any shared-surface change they need from Platform.
  • Roadmap doc: one row per section — target beta date, target live date, owning team. Lives in docs/ alongside the existing docs, same convention.
  • This doc: keep it updated in docs/ once the team names and section list are filled in, so it's a repo artifact, not tribal knowledge someone has to re-explain to the next new hire.
