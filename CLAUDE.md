## Project Overview

**FMS (Faculty Management System)** — multi-tenant faculty/staff/academics management platform for a group of colleges, organized along two tenancy axes: **Locations** (campus/city) → **Colleges** (belong to a location), with a `SUPER_ADMIN` above both.

- **Framework:** Next.js **16.2.9** (App Router, Turbopack; `src/proxy.ts` replaces `middleware.ts` → `proxy()` + `config.matcher`), React **19.2**, TypeScript **5.9** (strict).
- **Backend:** Firebase — Auth (client SDK), **Firestore** + **Storage** via `firebase-admin` **14** server-side only. No SQL database, no Redis, no external message queue.
- **UI:** Tailwind CSS 4, Radix/shadcn (`src/components/ui`), Zustand (`src/store`) + TanStack Query, react-hook-form + zod 4.
- **Domain libs:** exceljs (Excel import/export), jspdf/html2canvas (client PDF), puppeteer/@sparticuz/chromium (server PDF), face-api.js + leaflet (attendance geofence/face match), nodemailer (email), react-qr-code.
- **Scheduled jobs:** `functions/` (Firebase Cloud Functions v2, Node 20) — a thin scheduler that pings the app's own `/api/cron/attendance-not-posted` every 15 min IST.
- **Hosting:** Vercel (serverless; see `next.config.ts` `outputFileTracingIncludes` for the PDF route's Chromium binary).

### Read-only access for RESIGNED / RETIRED faculty (every college, no switch)

There is **no env switch** (the old `READ_ONLY_FACULTY_COLLEGES` is gone and ignored): it applies to every college.

- **What it does:** a login (role `PANEL_MEMBER`, `HOD` or `DEPARTMENT_OFFICE`) linked to a faculty record whose `facultyMembers.status` is `RESIGNED`/`RETIRED` still signs in (account, role, `isActive`, Firebase Auth are never touched) but is **read-only**: it may only GET its own profile/history (the allow-list in `src/lib/auth/readOnlyAccess.ts`); every write and every other read is denied (401), and it holds no seat authority. State is **derived from `facultyMembers.status`** - nothing is stored on `users`; setting the status back to a non-exited value restores access (it never restores a vacated seat).
- **UI:** `useReadOnlyAccess()` hides every control that changes something - My Profile (Edit Details, photo upload/delete, Change Password), section Edit buttons, attendance check-in/out/face registration, leave Apply/Edit/Cancel/proof upload, notification "mark as read", and the menu entries they can't open. `ReadOnlyAccessGate` blocks `/edit` and other write URLs. `authStore.setUser` never drops the flag when a caller replaces the user with a copy that doesn't mention it (`useAuth` states it explicitly, true/false, after each session answer). Hiding is cosmetic - the API guards are the enforcement. Change Password is a client-side Firebase call, so it can only be hidden, not API-blocked.
- **How it works:** `src/proxy.ts` stamps `x-fms-method`/`x-fms-path` on every `/api` request (always overwriting the client's); `src/lib/auth/liveRoles.ts` applies the rule after its 20 s cache; `/api/auth/session` returns a derived `readOnlyAccess` flag for the UI (`ReadOnlyAccessGate`). No protected file is involved.
- **Related behaviour:** saving a faculty member who is RESIGNED/RETIRED vacates the seats they hold (`src/lib/faculty/vacateSeatsOnExit.ts`, retried on every later save; outcome in `facultyMembers.seatVacateStatus`); `assignSeat` and the Department Office route refuse to give a seat to an exited person (`src/lib/roles/seatEligibility.ts`).
- **Cost:** one extra single-document query per faculty-capable login per 20 s window (`facultyMembers.where("userUid","==",uid).limit(1)`), plus one at sign-in. Other roles pay nothing. If that lookup fails, writes are denied (reads carry on).
- **Reinstating:** set the status back to a non-exited value - access returns within 20 s. Nothing is stored on `users`, and a vacated seat is never auto-restored.
- **Safety net:** `src/app/api/routeGuards.inventory.test.ts` fails if a new mutating API route has no role guard (so it could never be denied to a read-only person) and proves every guarded mutating route denies a RESIGNED/RETIRED login.
- **Pickers:** the Department Office, Sub-HOD, Role Assignments (Assign) and Leave Handover pickers leave out RESIGNED/RETIRED people (`exitedFacultyUids` in `src/lib/auth/readOnlyFacultyLookup.ts`; `users` / `role-seats` GET add an additive `facultyExited` flag, the two leave pickers filter server-side). Stored records, historical handovers and the other pickers are untouched.

### Feature switch: faculty single source of truth

`FACULTY_SINGLE_SOURCE_COLLEGES` = comma-separated college ids. **Empty/unset = OFF for everyone** (the default; the other colleges stay byte-identical).

- **Model:** a faculty member's details live on the `facultyMembers` record; the login (`users`) is identity/access plus a derived mirror (`name`, `profilePhotoUrl`, ...). Never add a faculty-owned field to `users`.
- **What it does (listed colleges only):** (1) the Super-Admin user list/detail (`api/admin/users`, `[uid]`) and the college `users/[uid]` GET show the faculty record's value where it is non-empty (`mergeFacultyWithLogin` in `src/lib/faculty/singleSource.ts`; identity/access fields stay the login's; nothing is hidden when the faculty value is blank); (2) `users/me` PATCH (callers who hold the Faculty role, not Principal/VP) and `users/[uid]` PATCH refuse **409 `FACULTY_RECORD_IS_SOURCE`**, before any write, when the body carries profile content (personal details, `academicProfile`) or a *changed* name/employee id/mobile for a faculty-linked person - nothing is changed; (3) `faculty/me` GET adds `editViaFacultyRecord` and the shared My Profile edit page (`MyProfileModuleEditPage`) and Principal's staff module edit page then save to the faculty record (`faculty/me` / `faculty/[id]` PATCH, section-scoped) instead. **No new permission is granted** - the same callers use routes they already could.
- **Keep in step:** `FACULTY_PERSONAL_KEYS` must list every key `buildPersonalDetailsUpdate` can write (a unit test enforces it).
- **Cost:** unlisted colleges: zero extra reads. Listed: one `facultyMembers` lookup only on a guarded login-side write.
- **Switching OFF:** remove the id and restart; nothing stored needs undoing (the guard never deleted or rewrote anything; a login's own copy of a profile, if one ever existed, is still stored).

### Academic scope: Years Taught, shared years, course length

- **Empty Years Taught = NOT CONFIGURED, never "all years".** `resolveTaughtYears` / `admitYear` (`src/lib/college/taughtYears.ts`) are the one answer; section create/edit/reassign, unassigned student create, exam configuration and subject assignment refuse a year the department doesn't teach (a department with none gets a "no Years Taught set" 400). Pickers show no years rather than every year. Never write `years.length > 0 && !years.includes(y)` or `years.length ? filter : all`.
- **Editing Years Taught is guarded** (`checkYearsEdit`, `src/lib/departments/yearDependents.ts`, called from `college/departments` PATCH for per-course set/clear and the flat field): refused 409 if sections / students (not graduated) / teaching assignments / timetable slots / subject assignments / timings / exam configurations are still filed under a (course, year) the edit would take away, 400 if it would leave a department with no years. A year still covered by a shared-year manager is not "lost". Nothing is written on a refusal.
- **Course Catalog is the source of the Course docs' name / code / length** (`catalogSync.ts`, `course-catalog/[id]` PATCH): saving name/code/duration syncs every department's Course doc in the same atomic batch (and repairs drift), refuses to shorten a course while years past the new length are taught or hold data, and a rename refreshes the live copies (`students.course`, `sections.courseName`, `teachingAssignments.courseName`). Display snapshots (exam circulars, mid schedules, candidate applications) are not rewritten.
- **Department rename never touches another department's rows** (`renameCascade.ts`): the by-id pass skips a doc whose stored name is another department's current name (teaching assignments store the SECTION's department name beside the COURSE owner's id), and an existing id is never overwritten - only a missing one is stamped.
- **No assumed course shape.** Year lists come from `Course.durationYears` (`courseYearNumbers`, `selectableYears`); semesters from the course's own `courseYearTimings` (`semesterPlan`, `useCourseSemesterPlan`) with a single labelled fallback of 2/year only when a course has none.

### Previous Teaching Assignments (free text)

- **Where:** `facultyMembers.previousTeachingAssignments` - a list of `{ id, source: INTERNAL|EXTERNAL, collegeName (External only), academicYear, course, year, semester, subject, passPercentage }`, every field free text. Separate from the `teachingAssignments` collection (current/structured/legacy `isPast` rows), which the feature never touches; old `isPast` rows stay listed and editable under "Previous".
- **Who writes it:** the faculty member themselves (`PATCH /api/college/faculty/me`, from their own Teaching Load page - the only self-editable part of that module; `isSelfEditDisabled` in `profileModules.ts`) and HOD/Principal (`PATCH /api/college/faculty/[id]`, the Add wizard via `POST /api/college/faculty` and `link-hod`).
- **Never lose a row:** editors send `previousTeachingAssignmentsLoadedIds`; the server keeps any stored row the editor never loaded (`mergePreviousTeachingAssignments`) and drops only rows it loaded and removed, so a stale edit page cannot erase what someone else added. Rules (trim, External needs a College Name, caps) live in `src/lib/faculty/previousTeaching.ts`.
- **Shown in:** the Teaching Load view (`TeachingLoadTable`) and the resume ("Previous Teaching Assignments" table).

### Students: Roll No optional, Student Mobile No required and globally unique

- **Roll No is REQUIRED in the bulk import** (`students/import-excel`, both the unassigned and the section-placed path: a row without one is skipped with "Roll No is required") and stays **optional on the single Add Student form and on edit**: the Office may still enrol one student before a roll number exists. A student with none is stored with `rollNumber: ""` (no `rollNumberUpper`, no roll claim) - the lists already order and display them (`compareStudentsForList`). When a roll is given it is still unique across ALL colleges (`studentUsernames` claim, `rollIdentity.ts`); a **login needs a roll** (`provisionStudentLogin` refuses a roll-less student with a clear message, import/bulk-create-login report it per row).
- **Student Mobile No is REQUIRED and unique across ALL students of ALL colleges** (`src/lib/students/studentMobile.ts`): 10 digits starting 6-9 (a leading +91/91/0, spaces and dashes are dropped and the 10-digit form is what is stored). Blank is refused by import-excel (that row), `POST /students` (400) and the roster-details edit in `students/[id]` PATCH (a number can be changed, never cleared). Claimed atomically in the global `studentMobileKeys/{number}` collection (`{ studentId, collegeId }`, like the roll registry); a claim is live only while its student exists and still holds the number, so deleting a student or changing a number frees it with nothing to release. A clash with a student of another college is reported as "already used by a student of another college" - never naming them.
- **Legacy students:** only a *changed* number is validated/claimed - an unchanged value is never re-judged, and a legacy student saved with no number may still be saved without one until it is entered. Students saved before the claims existed are covered for their OWN college by an exact-value lookup; another college's legacy students only after `scripts/backfill-student-mobile-keys.mjs` (global, dry run by default) has created their claims (it also reports duplicates, blanks and non-mobile values).
- **Why:** the mobile number is the reference a later "Roll No + Student Mobile No" import will use to give each student their roll number (then logins are created from the roll).
- **The import also reads the college's own admission sheet** (Sl.No, Roll.No, Admission.No, Student Name ... Mother Mobile.No) as it is (`src/lib/students/importHeaders.ts`, with the sheet's real header row pinned in its test): Sl.No is ignored, "Category" is the roster's Caste and the sheet's "Caste" its Sub Caste, day-first dates become YYYY-MM-DD. Its extra columns are roster fields (`ADMISSION_SHEET_TEXT_KEYS` in `rosterFields.ts`: seat type, parents' occupation / income, SSC / Inter / Diploma / Degree details), stored as typed and Office-managed (not in `STUDENT_SELF_EDITABLE_KEYS`). A header the importer does not know still rejects the file.

### Students edit their own details

- `PATCH /api/college/student/me/profile` (STUDENT only, resolved from `session.uid`): a student may change only the keys in `STUDENT_SELF_EDITABLE_KEYS` (`src/lib/students/selfEdit.ts`) - personal (blood group, nationality, mother tongue, hosteller, handicap, identification marks), contact & address, family & guardian, bank (account/bank/IFSC), "studied outside AP"/"family ID" answers. Everything else (Roll No, name, course/department/year/section, admission & entrance data, gender, DOB, caste/religion, Aadhar, ration card, remarks, status) stays with the College Office and is refused 403 `FIELD_NOT_EDITABLE`; nothing is written on a refusal.
- Only CHANGED fields are written (the page sends a diff), so a stale form can't overwrite an Office edit. Phones are stored as 10 digits, email lower-case, IFSC upper-case, a cleared field as `null`; "No" answers clear their dependent details and "permanent same as temporary" keeps both addresses identical.
- **Student Mobile No** is editable by the student only once a Roll No exists (until then the Office uses it to map the roll), never clearable, and goes through the same global claim as everywhere (`studentMobile.ts`).
- **Photo:** `PATCH /api/college/student/me/photo` writes the student record + `users/{uid}` + `systemUsers/{uid}` in ONE batch (record is the source of truth, the login only feeds the avatar); `upload/profile-photo` accepts STUDENT and forces their own uid path. The Office's photo edit (`students/[id]`) now mirrors to the login the same way.
- Each save writes an audit entry (`STUDENT_DETAILS_UPDATED`, `self: true`, field names only).

### Update student data (College Office > Students > Import > "Update student data")

- Third tab beside "Add students" and "Map roll numbers" (which is untouched). The Office picks detail fields, downloads a template (Student Mobile No + the picked columns), uploads it; each row finds its student by **Student Mobile No** and updates only those fields. Rules (`lib/students/bulkUpdate.ts`): blank cell = nothing (never clears); student blank -> FILL; same value -> left alone; different -> OVERWRITE (unless "Fill blanks only"); one bad cell skips that student whole. Allow-list = the `ROSTER_DETAIL_GROUPS` fields minus `mobileNo` - never Roll No, name, course/department/year/section, status.
- `POST /api/college/students/bulk-update/{preview,apply}` (COLLEGE_OFFICE): preview whole file (<=2000 rows, writes nothing); apply in chunks of <=100 rows with one `runId`. Both use `bulkUpdateResolve.ts` (apply re-resolves and re-classifies inside a per-student transaction). Each changed student writes its fields + a backup row `colleges/{c}/studentBulkUpdates/{runId}/rows/{studentId}` (`before` / `after` of every changed field) in the SAME transaction, plus a `STUDENT_DETAILS_UPDATED` audit entry (`via: "Bulk Update Students"`). Does not touch `mobileNo`, `rollNumber`, the mobile/roll registries or logins. Dependent answers (e.g. Handicapped Type) are never auto-cleared - only warned.
- Tests: `bulkUpdate.test.ts` (incl. parity with `selfEdit`), `bulkUpdate.emulator.test.ts` (real routes).

### Faculty college email (the login) - College Office only

- A faculty member's **college email is their login** and lives in five places: Firebase Auth, `facultyMembers.collegeEmail`, `users/{uid}.email`, `users/{uid}.collegeEmail` (some accounts), `systemUsers/{uid}.email`. It is changed ONLY by the College Office (**College Office > Faculty > Change College Email**, `PATCH /api/college/faculty/[id]/college-email`, `lib/faculty/changeCollegeEmail.ts`), keyed on the **Employee ID** (the request must carry the record's Employee ID; it is never changed). Employee-ID sign-in reads the email from Auth, so it keeps working and resolves to the new address.
- Write order: `emailChangePending` marker -> Firebase Auth -> ONE batch (record + users + systemUsers + `collegeEmailHistory` + marker cleared + `sessionsValidAfter`); a failed batch restores the old Auth email; re-sending the same new email finishes an interrupted change. Refused (nothing written): Employee ID mismatch, invalid/taken address (Auth, faculty, staff, users - case-insensitive), and **`EMAIL_OUT_OF_SYNC`** when the record's email differs from the login's (needs manual review - never auto-fixed; `scripts/audit-faculty-email-sync.mjs` is a read-only report).
- **Signed out on every device:** `users/{uid}.sessionsValidAfter` (unix s) + the session cookie's `iat` (added by `api/auth/session`): `liveRoles.applySessionRevocation` denies every cookie issued before it (<=20 s), `api/auth/session` refuses an older Firebase token (401 `SESSION_REVOKED`), refresh tokens are revoked, and `useSessionRevocationWatch` (dashboard layout, polls `api/auth/session-check` each minute / on focus) signs open tabs out. They sign in again with Employee ID + the same password, or the new email. Only users with the field are affected; `verifySession.ts` is unchanged.
- **Bulk update:** College Office > Faculty > **Bulk Update College Emails** (`/college-office/faculty/college-email-import`, `POST /api/college/faculty/college-email-import`, `lib/faculty/bulkCollegeEmail.ts`): an Excel/CSV of Employee ID + New College Email. Every row runs the SAME `changeFacultyCollegeEmail` as the single button (so identical rules, side effects, sign-out and notification); a refused row changes nothing and never stops later rows. Row results: `UPDATED`, `UNCHANGED` ("Already the same college email - no update was made"), `FAILED` with a reason (taken address, not found, out of sync, invalid, repeated Employee ID / email in the file - first row wins). Rows are matched on Employee ID case-insensitively within the college, processed strictly one at a time, sent in chunks of 25 (server cap 50). An address that is currently another faculty member's can't be given to a row in the same upload (change them first, then upload again - already-applied rows report "already same"). The page-side/file rules live in client-safe `bulkCollegeEmailRows.ts`.
- In-app notification only (`COLLEGE_EMAIL_CHANGED`); no email is sent. Other paths that used to change the login email half-way (`faculty/[id]` PATCH, `college/users/[uid]` PATCH, `admin/users/[uid]` PATCH, `users/me` PATCH) now refuse a *different* faculty email with 409 `COLLEGE_EMAIL_MANAGED_BY_OFFICE`; unchanged values are ignored.

### Tenancy & roles (from `src/types/core.ts` — single source of truth)

- **Location-scoped roles** (`ADMINISTRATION`, `HR_ADMIN`, `ADMIN_OFFICE`, `LOCATION_DEPT_HEAD`) — profiles at `locations/{id}/locationUsers/{uid}`.
- **College-scoped roles** (`PRINCIPAL`, `VICE_PRINCIPAL`, `HOD`, `COLLEGE_OFFICE`, `PANEL_MEMBER`, `STUDENT`, internal-office roles, ...) — profiles at `colleges/{id}/users/{uid}`.
- **Global roles** (`SUPER_ADMIN`, `MANAGEMENT`, `FINANCE`, `PURCHASE_DEPT`) — profiles in `systemUsers/{uid}`.
- `COLLEGE_ADMIN`/`DIRECTOR` are normalized to `PRINCIPAL` at session time; `DEPARTMENT_OFFICE` normalized to `HOD` — real role preserved in `realRole`.
- `ROLE_LEVEL` (0–6) + `ROLE_SCOPE` drive coarse page gating in `proxy.ts` and role inheritance (`rolesInheritedBy`, `canRoleAccessRole`). Real data isolation happens **per API route** via `verifySession.ts` + `lib/departments/scope.ts`.

### Auth flow

1. Client Firebase Auth → `POST /api/auth/session` verifies the ID token, resolves role/collegeId/locationId, sets signed (HMAC-SHA256, Web Crypto) httpOnly `fms-session` cookie (24h).
2. `src/proxy.ts` gates dashboard **pages** only.
3. Every API route guards itself through `src/lib/auth/verifySession.ts`. Bearer-token routes (cron, public APIs) use `verifyFirebaseToken.ts`.
4. Firestore security rules (`firestore.rules`) are a second, coarser layer: they see only `{role, collegeId, locationId}` claims and **cannot** distinguish seat-holders or normalized roles.

## Coding Conventions & Guardrails

### Style

- Path alias `@/*` → `src/*` (mirrored in `vitest.config.mts`). Import from `@/types` barrel, `@/lib/...`, `@/components/...`.
- API routes: named exports `export async function GET/POST/PATCH/DELETE`, `export const dynamic = "force-dynamic"` when reads must not be cached; dynamic segments receive `{ params }: { params: Promise<{ id: string }> }` (Next.js 16 — params are async).
- Error handling pattern per route: `try { ... } catch (err)` → re-check sentinel errors thrown by guards (`UNAUTHORIZED`, `NO_COLLEGE_CONTEXT`) → 401; validation failures → `NextResponse.json({ error }, { status: 400 })`; optimistic-concurrency misses → **409**; everything else → `console.error("[route-name]", err)` + 500. Never leak internals.
- Server-side Firebase **always** via `getAdminDb()`/`getAdminAuth()`/`getAdminStorage()` from `@/lib/firebase/admin` — never the client SDK in API routes. Multi-doc writes use `db.runTransaction` or `ChunkedBatch` (`lib/firestore/chunkedBatch.ts`) — Firestore caps batches at 500.
- All date-of-record logic in attendance goes through `lib/attendance/istTime.ts` (`istDateKey`, `istMidnightUTC`, `getISTParts`) — never ambient `Date` getters; all colleges are IST (`Asia/Kolkata`).
- Types live in `src/types/*.ts` (one file per domain); types import `Timestamp` from `firebase/firestore`. Cross-cutting events extend the `AuditLog` and `AppNotification` unions in `core.ts`.
- Notifications via `lib/notify.ts` (`notify`, `notifyRole`) — not hand-rolled per route. UI toasts via `useToast()`; auth via `useAuth()` + Zustand `authStore`.
- Naming: `camelCase` files in lib, `PascalCase.tsx` components, route folders kebab-case. Zod for request validation in newer routes.

### Strict boundaries — do NOT modify without permission

1. **`src/lib/auth/verifySession.ts`** — imported by ~279 of 290 API route files. `requireRole` deliberately *rewrites* roles (HOD-seat resolution); changing resolution order changes ~420 `role === "HOD"` checks.
2. **`src/lib/departments/scope.ts`** — the department authorization boundary; three non-interchangeable scope functions (`editableDepartmentNames ⊃ facultyManageableDepartmentNames ⊃ ownDepartmentNames`).
3. **`firestore.rules`** — deployed separately by hand; repo file is ahead of the live ruleset. OR-combined matching means adding a second `match` block never tightens anything.
