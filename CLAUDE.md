## Project Overview

**FMS (Faculty Management System)** — multi-tenant faculty/staff/academics management platform for a group of colleges, organized along two tenancy axes: **Locations** (campus/city) → **Colleges** (belong to a location), with a `SUPER_ADMIN` above both.

- **Framework:** Next.js **16.3.8** (App Router, Turbopack; `src/proxy.ts` replaces `middleware.ts` → `proxy()` + `config.matcher`), React **19.2**, TypeScript **5.9** (strict).
- **Backend:** Firebase — Auth (client SDK), **Firestore** + **Storage** via `firebase-admin` **14** server-side only. No SQL database, no Redis, no external message queue.
- **UI:** Tailwind CSS 4, Radix/shadcn (`src/components/ui`), Zustand (`src/store`) + TanStack Query, react-hook-form + zod 4.
- **Domain libs:** exceljs (Excel import/export), jspdf/html2canvas (client PDF), puppeteer/@sparticuz/chromium (server PDF), face-api.js + leaflet (attendance geofence/face match), nodemailer (email), react-qr-code.
- **Scheduled jobs:** `functions/` (Firebase Cloud Functions v2, Node 20) — a thin scheduler that pings the app's own `/api/cron/attendance-not-posted` every 15 min IST.
- **Hosting:** Vercel (serverless; see `next.config.ts` `outputFileTracingIncludes` for the PDF route's Chromium binary).

### Read-only access for RESIGNED / RETIRED faculty (every college, no switch)

There is **no env switch** (the old `READ_ONLY_FACULTY_COLLEGES` is gone and ignored): it applies to every college.

- **What it does:** a login (role `PANEL_MEMBER`, `HOD` or `DEPARTMENT_OFFICE`) linked to a faculty record whose `facultyMembers.status` is `RESIGNED`/`RETIRED` still signs in (account, role, `isActive`, Firebase Auth are never touched) but is **read-only**: it may only GET its own profile/history (the allow-list in `src/lib/auth/readOnlyAccess.ts`); every write and every other read is denied (401), and it holds no seat authority. State is **derived from `facultyMembers.status`** - nothing is stored on `users`; setting the status back to a non-exited value restores access (it never restores a vacated seat).
- **UI:** `useReadOnlyAccess()` hides every control that changes something - My Profile (Edit Details, photo upload/delete, Change Password), section Edit buttons, attendance check-in/out/face registration, leave Apply/Edit/Cancel/proof upload, notification "mark as read", and the menu entries they can't open. `ReadOnlyAccessGate` blocks `/edit` and other write URLs. `authStore.setUser` never drops the flag when a caller replaces the user with a copy that doesn't mention it (`useAuth` states it explicitly, true/false, after each session answer). Hiding is cosmetic - the API guards are the enforcement. Change Password is a client-side Firebase call, so it can only be hidden, not API-blocked.
- **How it works:** `src/proxy.ts` stamps `x-fms-method`/`x-fms-path` on every `/api` request (always overwriting the client's); `src/lib/auth/liveRoles.ts` applies the rule after its 20 s cache; `/api/auth/session` returns a derived `readOnlyAccess` flag for the UI (`ReadOnlyAccessGate`). No protected file is involved.
- **Related behaviour:** saving a faculty member who is RESIGNED/RETIRED vacates the seats they hold (`src/lib/faculty/vacateSeatsOnExit.ts`, retried on every later save; outcome in `facultyMembers.seatVacateStatus`); `assignSeat` and the Department Office route refuse to give a seat to an exited person (`src/lib/roles/seatEligibility.ts`).
- **Cost:** one extra single-document query per faculty-capable login per 20 s window (`facultyMembers.where("userUid","==",uid).limit(1)`), plus one at sign-in. Other roles pay nothing. If that lookup fails, writes are denied (reads carry on).
- **Reinstating:** set the status back to a non-exited value - access returns within 20 s. Nothing is stored on `users`, and a vacated seat is never auto-restored.
- **Safety net:** `src/app/api/routeGuards.inventory.test.ts` fails if a new mutating API route has no role guard (so it could never be denied to a read-only person) and proves every guarded mutating route denies a RESIGNED/RETIRED login.
- **Pickers:** the Department Office, Sub-HOD, Role Assignments (Assign) and Leave Handover pickers leave out RESIGNED/RETIRED people (`exitedFacultyUids` in `src/lib/auth/readOnlyFacultyLookup.ts`; `users` / `role-seats` GET add an additive `facultyExited` flag, the two leave pickers filter server-side). Stored records, historical handovers and the other pickers are untouched.

### Feature switch: faculty single source of truth

`FACULTY_SINGLE_SOURCE_COLLEGES` = comma-separated college ids. **Empty/unset = OFF for everyone** (the default; the other colleges stay byte-identical).

- **Model:** a faculty member's details live on the `facultyMembers` record; the login (`users`) is identity/access plus a derived mirror (`name`, `profilePhotoUrl`, ...). Never add a faculty-owned field to `users`.
- **What it does (listed colleges only):** (1) the Super-Admin user list/detail (`api/admin/users`, `[uid]`) and the college `users/[uid]` GET show the faculty record's value where it is non-empty (`mergeFacultyWithLogin` in `src/lib/faculty/singleSource.ts`; identity/access fields stay the login's; nothing is hidden when the faculty value is blank); (2) `users/me` PATCH (callers who hold the Faculty role, not Principal/VP) and `users/[uid]` PATCH refuse **409 `FACULTY_RECORD_IS_SOURCE`**, before any write, when the body carries profile content (personal details, `academicProfile`) or a *changed* name/employee id/mobile for a faculty-linked person - nothing is changed; (3) `faculty/me` GET adds `editViaFacultyRecord` and the shared My Profile edit page (`MyProfileModuleEditPage`) and Principal's staff module edit page then save to the faculty record (`faculty/me` / `faculty/[id]` PATCH, section-scoped) instead. **No new permission is granted** - the same callers use routes they already could.
- **Keep in step:** `FACULTY_PERSONAL_KEYS` must list every key `buildPersonalDetailsUpdate` can write (a unit test enforces it).
- **Cost:** unlisted colleges: zero extra reads. Listed: one `facultyMembers` lookup only on a guarded login-side write.
- **Switching OFF:** remove the id and restart; nothing stored needs undoing (the guard never deleted or rewrote anything; a login's own copy of a profile, if one ever existed, is still stored).

### Academic scope: Years Taught, shared years, course length

- **Empty Years Taught = NOT CONFIGURED, never "all years".** `resolveTaughtYears` / `admitYear` (`src/lib/college/taughtYears.ts`) are the one answer; section create/edit/reassign, unassigned student create, exam configuration and subject assignment refuse a year the department doesn't teach (a department with none gets a "no Years Taught set" 400). Pickers show no years rather than every year. Never write `years.length > 0 && !years.includes(y)` or `years.length ? filter : all`.
- **Editing Years Taught is guarded** (`checkYearsEdit`, `src/lib/departments/yearDependents.ts`, called from `college/departments` PATCH for per-course set/clear and the flat field): refused 409 if sections / students (not graduated) / teaching assignments / timetable slots / subject assignments / timings / exam configurations are still filed under a (course, year) the edit would take away, 400 if it would leave a department with no years. A year still covered by a shared-year manager is not "lost". Nothing is written on a refusal.
- **Course Catalog is the source of the Course docs' name / code / length** (`catalogSync.ts`, `course-catalog/[id]` PATCH): saving name/code/duration syncs every department's Course doc in the same atomic batch (and repairs drift), refuses to shorten a course while years past the new length are taught or hold data, and a rename refreshes the live copies (`students.course`, `sections.courseName`, `teachingAssignments.courseName`). Display snapshots (exam circulars, mid schedules, candidate applications) are not rewritten.
- **Department rename never touches another department's rows** (`renameCascade.ts`): the by-id pass skips a doc whose stored name is another department's current name (teaching assignments store the SECTION's department name beside the COURSE owner's id), and an existing id is never overwritten - only a missing one is stamped.
- **No assumed course shape.** Year lists come from `Course.durationYears` (`courseYearNumbers`, `selectableYears`); semesters from the course's own `courseYearTimings` (`semesterPlan`, `useCourseSemesterPlan`) with a single labelled fallback of 2/year only when a course has none.

Separate from the `teachingAssignments` collection (current/structured/legacy `isPast` rows), which the feature never touches; old `isPast` rows stay listed and editable under "Previous".

### Students: Regd. No optional, Student Mobile No required and globally unique

- **The bulk import needs a Regd. No OR a Student Mobile No - either one is enough** (`students/import-excel`, both the unassigned and the section-placed path): a row with a roll and no mobile imports, a row with a mobile and no roll imports (its roll is mapped on later by that mobile), and a row with neither is skipped with `ROLL_OR_MOBILE_REQUIRED_MESSAGE` ("Regd. No or Student Mobile No is required - give at least one"). Whatever is given is still validated and claimed. The roll stays **optional on the single Add Student form and on edit** (which still require a mobile): the Office may still enrol one student before a Regd. No exists. A student with none is stored with `rollNumber: ""` (no `rollNumberUpper`, no roll claim) - the lists already order and display them (`compareStudentsForList`). When a roll is given it is still unique across ALL colleges (`studentUsernames` claim, `rollIdentity.ts`); a **login needs a roll** (`provisionStudentLogin` refuses a roll-less student with a clear message, import/bulk-create-login report it per row).
- **Student Mobile No is unique across ALL students of ALL colleges** (required on the single Add form and in edits; in the bulk import it is required only when the row has no Regd. No) (`src/lib/students/studentMobile.ts`): 10 digits starting 6-9 (a leading +91/91/0, spaces and dashes are dropped and the 10-digit form is what is stored). Blank is refused by import-excel (that row, unless it has a Regd. No), `POST /students` (400) and the roster-details edit in `students/[id]` PATCH (a number can be changed, never cleared). Claimed atomically in the global `studentMobileKeys/{number}` collection (`{ studentId, collegeId }`, like the roll registry); a claim is live only while its student exists and still holds the number, so deleting a student or changing a number frees it with nothing to release. A clash with a student of another college is reported as "already used by a student of another college" - never naming them.
- **Legacy students:** only a *changed* number is validated/claimed - an unchanged value is never re-judged, and a legacy student saved with no number may still be saved without one until it is entered. Students saved before the claims existed are covered for their OWN college by an exact-value lookup; another college's legacy students only after `scripts/backfill-student-mobile-keys.mjs` (global, dry run by default) has created their claims (it also reports duplicates, blanks and non-mobile values).
- **Why:** the mobile number is the reference a later "Regd. No + Student Mobile No" import will use to give each student their Regd. No (then logins are created from the roll).
- **The import also reads the college's own admission sheet** (Sl.No, Roll.No, Admission.No, Student Name ... Mother Mobile.No) as it is (`src/lib/students/importHeaders.ts`, with the sheet's real header row pinned in its test): Sl.No is ignored, "Category" is the roster's Caste and the sheet's "Caste" its Sub Caste, day-first dates become YYYY-MM-DD. Its extra columns are roster fields (`ADMISSION_SHEET_TEXT_KEYS` in `rosterFields.ts`: seat type, parents' occupation / income, SSC / Inter / Diploma / Degree details), stored as typed and Office-managed (not in `STUDENT_SELF_EDITABLE_KEYS`). A header the importer does not know still rejects the file.

### Faculty college email (the login) - College Office only

- A faculty member's **college email is their login** and lives in five places: Firebase Auth, `facultyMembers.collegeEmail`, `users/{uid}.email`, `users/{uid}.collegeEmail` (some accounts), `systemUsers/{uid}.email`. It is changed ONLY by the College Office (**College Office > Faculty > Change College Email**, `PATCH /api/college/faculty/[id]/college-email`, `lib/faculty/changeCollegeEmail.ts`), keyed on the **Employee ID** (the request must carry the record's Employee ID; it is never changed). Employee-ID sign-in reads the email from Auth, so it keeps working and resolves to the new address.
- Write order: `emailChangePending` marker -> Firebase Auth -> ONE batch (record + users + systemUsers + `collegeEmailHistory` + marker cleared + `sessionsValidAfter`); a failed batch restores the old Auth email; re-sending the same new email finishes an interrupted change. Refused (nothing written): Employee ID mismatch, invalid/taken address (Auth, faculty, staff, users - case-insensitive), and **`EMAIL_OUT_OF_SYNC`** when the record's email differs from the login's (needs manual review - never auto-fixed; `scripts/audit-faculty-email-sync.mjs` is a read-only report).
- **Signed out on every device:** `users/{uid}.sessionsValidAfter` (unix s) + the session cookie's `iat` (added by `api/auth/session`): `liveRoles.applySessionRevocation` denies every cookie issued before it (<=20 s), `api/auth/session` refuses an older Firebase token (401 `SESSION_REVOKED`), refresh tokens are revoked, and `useSessionRevocationWatch` (dashboard layout, polls `api/auth/session-check` each minute / on focus) signs open tabs out. They sign in again with Employee ID + the same password, or the new email. Only users with the field are affected; `verifySession.ts` is unchanged.
- **Bulk update:** College Office > Faculty > **Bulk Update College Emails** (`/college-office/faculty/college-email-import`, `POST /api/college/faculty/college-email-import`, `lib/faculty/bulkCollegeEmail.ts`): an Excel/CSV of Employee ID + New College Email. Every row runs the SAME `changeFacultyCollegeEmail` as the single button (so identical rules, side effects, sign-out and notification); a refused row changes nothing and never stops later rows. Row results: `UPDATED`, `UNCHANGED` ("Already the same college email - no update was made"), `FAILED` with a reason (taken address, not found, out of sync, invalid, repeated Employee ID / email in the file - first row wins). Rows are matched on Employee ID case-insensitively within the college, processed strictly one at a time, sent in chunks of 25 (server cap 50). An address that is currently another faculty member's can't be given to a row in the same upload (change them first, then upload again - already-applied rows report "already same"). The page-side/file rules live in client-safe `bulkCollegeEmailRows.ts`.
- In-app notification only (`COLLEGE_EMAIL_CHANGED`); no email is sent. Other paths that used to change the login email half-way (`faculty/[id]` PATCH, `college/users/[uid]` PATCH, `admin/users/[uid]` PATCH, `users/me` PATCH) now refuse a *different* faculty email with 409 `COLLEGE_EMAIL_MANAGED_BY_OFFICE`; unchanged values are ignored.

### Semester results (Exam Cell, grade based) - Phase 1

- **Who sees it:** the Exam Cell (Result Rules, import, sheets) and each **student** (`/student/results`, `GET /api/college/student/me/results` - own results from `session.uid`, PUBLISHED records of PUBLISHED sheets only, built by `studentResults.ts`: latest attempt per subject with every attempt kept, SGPA / CGPA per the show rules). HOD / Principal views are still to come.
- **Results Analysis** (`/exam-cell/results-analysis`, `/principal/results-analysis` for Principal + VP, `/hod/results-analysis`; shared `components/exams/ResultsAnalysisView.tsx`, `GET /api/college/exam-results/analytics`, stats in `analytics.ts`): PUBLISHED results only, per class (course + batch + semester), one branch or all. HODs are limited server-side to `editableDepartmentNames`. Shows students, pass % now vs Regular pass %, average / highest SGPA, backlogs, branch comparison, grade distribution, SGPA bands, subject-wise pass %, toppers and a backlog list (CSV). Charts are plain HTML, single-series (blue; status red only for failing grades, labelled).
- **Exam Cell pages:** Result Rules (`/exam-cell/result-rules`), import (`/exam-cell/semester-results/import`, `?batchId=` adds rows to a draft), sheets list and sheet page (Publish / Delete draft; each student's SGPA and CGPA as of that semester, from their PUBLISHED results plus that sheet - `studentStanding`). Student / HOD / Principal views are Phase 2.
- **Grades only, per branch:** a sheet is Regd. No + Subject Code + Grade for one course + **branch** (department; a 1st-year matches by core department too) + year + semester. No marks are imported - internal marks stay with the faculty's Internal Exam flow.
- **One upload, every branch:** the import page has no Branch pick - each student's own department (`secondaryDepartment` first, so a Basic Science 1st year goes to their core branch; a sub-department gets its own sheet) decides their sheet (`groupByBranch` in `importRows.ts`). One upload makes one draft per branch sharing an `uploadId` (parts of a big file join the same sheets); Supplementary / Revaluation pick the exam across branches (`targetExam` = exam type + held month, resolved per student). The sheets list offers **Publish all / Delete all** per upload (the same per-sheet PATCH / DELETE, one at a time). A meta with a `departmentId` still works for one branch.
- **Formulas are fixed** (`src/lib/examResults/gpa.ts`): SGPA = Σ(credits × grade points) / Σ credits of the semester (a failed subject stays in the divisor with 0 points; zero-credit subjects are left out but must still be passed); CGPA = Σ(semester credits × SGPA) / Σ semester credits, from exact values. **Per college** (`colleges/{id}/examResultRules/rules`): grade tables (default + per regulation; Absent / Malpractice / Withheld are just failing grades) and when SGPA / CGPA are shown - `ALL_PASSED` (withheld while any covered subject is failed) or `ALWAYS`. SGPA / CGPA are never stored; they are worked out each time, so they appear by themselves once a backlog is cleared.
- **Storage:** `semesterResultBatches/{id}` (one per imported sheet, DRAFT -> PUBLISHED) and `semesterResults/{batchId}_{studentId}` (one per student per sheet; credits / points / pass are snapshots taken at import). Students matched by Regd. No, subjects matched by college code only (credits from the subject record, not the file). Never map codes by position - that is what produced wrong SGPAs in the first real test.
- **Revaluation** (exam type `REVALUATION` + `revaluationOf` REGULAR|SUPPLEMENTARY on the batch; each record carries `revaluesBatchId`): re-grades subjects of one PUBLISHED sitting of the same academic year + semester (`applyRevaluationTargets`), once per subject per sitting; passed subjects may be revalued. **Best of two** (`applyRevaluations` / `betterResult` in `gpa.ts`: a pass beats a fail, else more points; a lower grade is kept as history only), and a subject's final result is its latest PASSING attempt (`finalPerSubject`) - a revaluation pass is never undone by a later failed supplementary.
- **What a sheet is** (`sheet.ts` `normalizeBatchMeta` / `completeFromTarget`): Course -> Regulation -> **Batch** (from the catalog's `regulationBatches`, via `exam-results/options`) -> Branch -> Year -> Semester -> Exam, plus **Exam held** (`examHeld`, "YYYY-MM", never a future month) for Regular / Supplementary. The academic year is DERIVED (Regular: batch start + year - 1, and its exam month may not fall before that year; Supplementary: from its month; Revaluation: the picked exam's). Supplementary and Revaluation **pick a published exam** of the same class (`targetBatchId`, listed by `exam-results/sittings`); a supplementary must be held after it, a revaluation takes its date and type. Pre-filled templates: `batches/[id]/template?for=SUPPLEMENTARY|REVALUATION`.
- **Batch is a note, not a refusal** (`batchMatches`, `wrongBatchFile`): each result goes to its Regd. No's student, filed under the exam picked (its batch decides academic year, regulation, class), whatever batch the student is in on record - a detained student moved to a junior batch, or one detained but not moved yet. Students whose batch on record differs (same, or ending the same year = lateral entry, counts as the sheet's; no batch = derived from section or year of study) are listed back as `otherBatch` and shown on the Check summary. The only stop: a file where 5+ students and over half are another batch ("check the batch picked") - nothing saved. Students with results already filed under the sheet's batch (any semester, `batchHistory`) are not noted. One Regular per semester **per batch**, so a detained student may write the Regular again under the new batch; the missing-students check skips a student who wrote that semester's Regular under another batch. Attempts are ordered by `examHeld`.
- **Checks before Publish** (sheet page, warnings only): optional "University SGPA" column compared with ours (`universitySgpa` on the record; "-" = withheld); Regular sheets list students of the batch + branch with no result (`missing` from the sheet GET) and students whose credit total differs from most.
- **Zero-credit subjects are Pass / Fail** (`validateResultRows`): any grade in the file is stored as `grade: "Pass"` (0 points), except one marked failing in the grade table (F, AB, MP, WH ...) -> `"Fail"`; the given value is kept in `gradeAsGiven`. Credit subjects still need a grade-table grade. They stay out of SGPA / CGPA and the letter-grade chart, but a Fail is a backlog.
- **Import rules** (`importRows.ts`, `import/route.ts`): no academic year after the college's current one; one Regular result per student per semester; Supplementary only for a subject whose earlier result is PUBLISHED, not yet passed, and not in a later academic year than the supplementary (attempts are ordered by academic year, then Regular before Supplementary); a student is saved whole or not at all (any refused row refuses all their rows). Published sheets are locked - corrections (revaluation) are Phase 3.

### Mid Question Bank (deadline first, faculty prepare per branch + subject)

- **Theory subjects only:** a subject whose master `type` is not `THEORY` (Practical, Tutorial, Project, Non-teaching) is left out of `teachingFor`, so it gets no notification, bank, setup or progress row (`isMidBankSubject` in `sections.ts`).
- **Flow:** Exam Cell > Mid Timings & Dates sets a **question bank deadline** per Course + Year + Semester + Mid (`midBankDeadlines`, before the Mid's exam dates when they exist) -> everyone teaching a subject of that semester (teaching assignments on the programme's sections of that year x subjects assigned to that semester, `teachingFor` in `lib/midBank/server.ts`) is notified and sees it at `/panel/mid-bank` -> a faculty member prepares a bank for **branch (section department) + subject + Mid** through a 4-step wizard (`PrepareBank`: 1 Sections, 2 Course Outcomes = units + COs, 3 CO-PO Mapping, 4 Question Bank), picking the sections it covers: at least one of their own, optionally colleagues' sections of that subject in that branch (they are notified and read it only). A section is in one bank only (`midBankSectionClaims`, claimed in a transaction). Banks lock when the deadline day ends (IST, `isDeadlineLocked`); the Exam Cell moving the date reopens them (kept in `extensions`). Exam Cell progress: `/exam-cell/question-banks/[deadlineId]`. Not tied to HOD > Mid Paper Setter (which stays for paper setting).
- **Data (additive):** `midBankDeadlines`, `midBankRules/{courseKey}__{regulation|ALL}` (Exam Cell > Mid Exams > Mid Configuration, `/exam-cell/mid-configuration` - the old `/exam-cell/settings` redirects there: regulation from the Course Catalog or ALL, units per Mid, `formats` = the question types the faculty may pick per question: one question, parts (a)+(b), (a)+(b)+(c) ... up to (e) - older rules' single `format` SINGLE | PARTS_AB | EITHER is read through `allowedFormats`, `marks`; a type with n parts needs >= n marks), `subjectOutcomes/{subjectId}__{branchKey}` (units, COs and the ticked CO -> PO/PSO mapping over PO1-PO11, PSO1, PSO2 - no strength levels, every CO mapped before a bank can start; entered by whoever prepares first, reused by Mid 2; editable while unused by anyone teaching it there, then by its author and the owners of banks using it, never removing a used unit/CO), `midQuestionBanks/{deadlineId}__{subjectId}__{branchKey}__{ownerFacultyId}` (sections, `viewerFacultyIds`, snapshot of the rules: units and marks stay as started; the question TYPES follow the Exam Cell's current rule - `bankFormats` - and a saved question keeps its own type, `formatsFor`), `.../questions/{unit}_{slot}` (`format`, `parts` with marks, `state`, `rev`, `textKeys`).
- **Units per Mid by subject** (`lib/midBank/unitSplit.ts` `midUnitsFor`, used only by `setupIssues`): the subject's Exam Cell exception (`midBankSubjectSplits/{subjectId}`, `MidSubjectSplitsCard`) -> the rule's split for the subject's unit count (`MidBankRules.unitSplits["5"]["2"]`, grid in `MidBankRulesCard`; the count = units entered in Course Outcomes) -> the rule's default `mids`. A bank snapshots its units at start. When the default names a unit the subject doesn't have, the issue goes to the Exam Cell (set a split for that count).
- **Rules** (`src/lib/midBank/`, unit-tested; re-run by the server in a transaction on every save): 10 questions per unit; a unit is complete when all 10 are complete and L2, L3, L4 each appear >= 3 times across parts; units open in the Mid's order; a complete question needs text (or a formula), >= 1 CO and one Bloom level per part; parts (a), (b) ... carry the faculty's split, which must add up to `marks`; exact duplicates in the bank refused, similar (Jaccard >= 0.8) warned; a completed unit can't be turned back (409); a stale `baseRev` is refused (409), never overwritten; only the owner writes, only before the deadline.
- **Editor:** drafts autosave (1.5 s, one request at a time); formulas are LaTeX in `$...$` rendered by KaTeX (`renderMath.ts`, shared by preview, review, PDF); images via `upload/mid-question-image` (owner, real PNG/JPEG, <= 1 MB, 40-2400 px); PDF built in the browser (`lib/pdf/midQuestionBankTemplate.ts`) once every unit is complete.
- Tests: `midBank.test.ts`; `midBank.emulator.test.ts` (real routes; needs the Firestore emulator).

### Internal marks: marks categories

- Exam Cell > Mid Configuration > Marks > "Marks categories" (`ExamMarksCategoriesCard`, `GET/POST /api/college/exam-marks-categories`, `PATCH/DELETE .../[id]`): a named internal / external max + components shared by a group of subjects (`examMarksCategories/{id}`: `examType`, `components`, `subjectIds`, `subjects` snapshot). Subjects are added many at a time (tick from a course's list, or paste codes resolved within one catalog course); a subject is in at most one category per exam type; skipped ones come back with the reason. Validation `lib/exams/marksBreakdown.ts`.
- **Every reader goes through `loadExamConfig`** (`lib/exams/internalExamMarks.ts`): the subject's category (`categoryForSubject`, `array-contains` on `subjectIds`) first, else `examConfigurations/{courseId}_year{y}_{type}` - used by `resolveExamConfigForBatch` (mentoring), `internal-exam-marks` GET (`include=config`) and POST, and `exam-configurations` GET `?subjectId`. Never read `examConfigurations` by id directly for a subject.
- **Locked once marks exist** (`marksEnteredFor`, `lib/exams/marksCategoriesServer.ts`): changing a category's breakdown, deleting it, or adding / removing a subject is refused (409 / skipped, naming who) when a batch of the subject has `enteredCount > 0` and its teaching assignment isn't `isPast`.

### Mid Timetable (Exam Cell builds, one per branch)

- **Flow:** Exam Cell > Mid Exams > Mid Timetable (`/exam-cell/mid-timetable`) - pick course + year + semester + Mid and the exam dates (pre-filled from Mid Timings & Dates when published - then the dates must sit inside them; otherwise the typed range is stored on the plan as `from`/`to`) -> a **plan** (`midExamPlans/{courseKey}__y{year}__s{sem}__m{mid}`: exam `days` - the Mid's dates without Sundays by default - and 1-3 `sessions` a day, shared by every branch) -> one **timetable per branch** (`midTimetables/{planId}__{branchKey}`, branch = section department): each Theory subject's day + session. The builder is ONE sheet like the printed one (branches x days, a column per session): click a cell to tick that branch's subject(s) - several in one cell are electives under a heading (`MidExamSlot.group`, e.g. "Professional Elective-IV"), optionally the same day for every branch that has the subject; Auto-fill all branches; Save draft / Publish all (per-branch PUTs), Unpublish per row. PDF: A4 landscape sheet (`downloadMidTimetable.ts` draws its own page - the shared htmlToPdf is portrait).
- **Subjects:** the branch's Theory subjects of that semester with teaching assignments (`teachingFor`, same as the question bank). **Rules** (`lib/midTimetable/rules.ts`, re-checked on every save): branch subjects only, each once; a plan day + session (several in one slot = electives); publish needs every subject placed; stale `rev` -> 409. A day / session a PUBLISHED timetable uses can't be removed from the plan (drafts just lose those placements).
- **Sessions per branch:** a plan has up to 6 sessions (`MAX_SESSIONS`); each branch has a usual session (`plan.branchSessions[branchKey]`, picked on its sheet row, saved at once; else `usualSessionOf` = most-used) kept for the whole Mid and saved on the timetable as `usualSessionId`. The sheet is one column per DAY; a cell shows a session's time only when it isn't the branch's usual one or there are two exams that day. `checkSlots(..., maxPerDay)`: at most `plan.maxPerDay` (default 2) exams a day per branch, never at overlapping times. Auto-fill uses the branch's usual session only. PDF: a Time column per branch (or one TIME line when every branch has the same). Students see only their own branch. Question papers take each paper's own session length; Exam Seating paired plans are one per session (`midGroups(..., time)` keeps the branches usually writing then; `examTime` = that session).
- **Postpone / prepone** (`POST mid-timetables/[planId]/reschedule`, `rescheduleSlots` in rules.ts): every exam of one day + session moves to another (any date, may be outside the Mid's dates - plan `days` are any dates spanning <= 3 months), for ONE branch or the WHOLE year, in one transaction; refused (409, nothing written) if the new slot already has an exam of an affected branch; `dryRun` previews. Published stays published; each moved slot keeps `movedFrom` (its first date - shown as "Rescheduled (was ...)" on screen and PDF); each timetable keeps `changes[]` (history on the builder, latest shown to viewers); faculty + students of affected PUBLISHED branches get `MID_TIMETABLE_CHANGED` (`batchNotify`). Unsaved sheet edits must be saved first.
- **Who sees it** (`GET /api/college/mid-timetables/published`, published only, `visibleTimetables`): students their own branch (current section), faculty the branches they teach, HOD also their departments, Exam Cell / Principal / VP every branch. Pages: `/student/mid-timetable`, `/panel/mid-timetable`, `/principal/mid-timetable` (VP too), each with PDF (`lib/pdf/midTimetableTemplate.ts`). A published timetable keeps its own copy of the sessions.

### Mid Question Paper (Exam Cell generates, nothing stored)

- **Template** (Mid Configuration > Question paper, `midPaperTemplates/{courseKey}__{regulation|ALL}`, `MidPaperTemplateCard`): a paper is 6 questions in three OR-pairs (1/2, 3/4, 5/6); `sequences` = the levels of Q1-6 for each level Q1 may start at (L2/L3/L4, entered in full); `units` = for a Mid of N units, the unit (by position in the Mid) of each question - every unit the same number (`cleanTemplate`); instruction line; optional max marks (default 3 x the bank's marks); `regdBoxes` = Regd. No boxes printed (default 12, 6-20; VWU numbers are 11 characters).
- **Generate** (`/exam-cell/mid-question-paper`, `POST /api/college/mid-question-papers`, EXAM_CELL / SUPER_ADMIN, writes NOTHING): pick a Mid timetable + exam date + Q1 level -> every subject on that date per branch is matched to its question bank (bank `deadlineId` == timetable `planId`, same subject + branch); only a COMPLETE bank gives a paper; `pickPaper` (`lib/midPaper/rules.ts`) picks 6 different complete questions of the slot's unit and level - a question's level is the one ALL its parts share - and lists shortages instead when a bank lacks them. Swap / Regenerate happen in the browser from the returned candidates.
- **PDF** (`lib/pdf/midQuestionPaperTemplate.ts`, portrait, MathJax formulas): code box (regulation number) + Regd. No boxes, letterhead, "I YEAR B.TECH I SEMESTER MID-1 EXAMINATION", academic year, subject, Branch & Sections (department code + the bank's sections), date and time (timetable session), max marks, instruction, the Course Outcomes used, UNIT rows + OR pairs with Marks / CO / BL / PO. File name `MID1_<academic year>_<reg>_<COURSE>_<I-I>_<branch>_<code>_<subject>_Sec-A-B-C.pdf`.

### Exam Seating: paired plans from the Mid timetable

- **PAIRED mode** (`ExamSeatingPlan.mode`, beside QUICK / LAYERED which are unchanged; card `PairedPlanCard` on `/exam-cell/seating`, `GET/POST /api/college/exam-seating/paired`): ONE arrangement for every exam day of the Mid - pick the Mid timetable(s) (`midSources`; several = years seated together) -> their groups (`midGroups`: one per timetable branch + year; plan keeps `midPlanIds`, `examDays`, `examTime`, shown as a date range by `seatingWhen`) -> put each group in a seat position (Seat A / B / C, ordered) -> tick rooms in fill order -> build. `allocatePaired` (`lib/exams/seatingPaired.ts`): rooms in the order picked, bench by bench, each seat takes the next student of its stream; a finished stream leaves its seat empty (the rest go on one per bench); students in a group go section by section (A, B ...), each section in Regd. No order (`groupStudents`); leftovers -> `unplaced`. Each student carries `bench`, `layer` (seat) and `group`; `validatePairedRoom` (PATCH) = valid bench/seat, used once, no bench holds two of one group. Seats are fixed by the build (no Move; delete the draft and rebuild); publish needs nobody unplaced.
- **PDFs** on the plan page (`lib/pdf/examSeatingTemplate.ts`): room door sheets (bench-wise, one page per 24-bench room), notice board (room -> section Regd. No ranges), signature sheets - one per exam day + subject x room x branch (`signatureSheetsHTML`; subjects from the plan's Mid timetables, electives "A / B"; plans without a timetable: one per room x branch) with only that branch's students in bench order.
- **Who sees it** (`GET /api/college/exam-seating/mine`, PUBLISHED plans only): students their room + bench/seat (`/student/exam-seat`), faculty / HOD the rooms where students of the sections they teach sit (`/panel/exam-seating`).

### Academics > Curriculum: one flow for subjects

- **Create (Subjects tab):** master subjects belong to a Course Catalog course + Regulation only (no department/year/semester), added by bulk import (`POST /api/college/subjects/import`, validate then commit, max 500 rows - the commit itself is chunked across multiple transactions, 150 rows/~450 writes each, so no single Firestore transaction exceeds its ~500-write ceiling; validation stays all-or-nothing, a conflict partway through a later chunk says so explicitly) or one at a time (`POST /api/college/subjects`). Both, and edit/delete (`subjects/[id]`), go through `SubjectMasterService` - never write `subjects` directly.
- **Identity:** inside one catalog course + regulation, Subject Code is unique; a repeated Subject Name is only a warning (the same title legitimately recurs under another code). The code is enforced against saved subjects AND by lock docs (`subjectKeys`, claimed in the same transaction; `claimSubjectKeys` is all-or-nothing). Code and Name are locked once the subject has a semester copy or teaching assignment - a new code means a new subject. Never add another way to create a subject or relax this: the Exam Cell matches results by code.
- **Assign (Assign tab):** the only way a subject reaches a department's semester is `POST /api/college/subject-semester-assignments/assign-by-code` (typed codes; `validate` then `commit`; one bad code = nothing assigned; existing copies are never overwritten). Checks live in `SubjectAssignService` (course ownership, Years Taught, semester in Course-Year Timings, regulation, active). There is no Excel assign, no assign by subject id, no hard delete.
- **Edits:** master fields, hours and credits always cascade to every semester copy through `SubjectMasterService.update` (teaching-assignment hours follow `hoursCascade.ts`, refused below placed timetable periods). Per-department hours/credits and core-department targeting are PATCH `subject-semester-assignments`; subject-level fields are never accepted there.
- **No silent defaults:** credits and L/T/P are required (an explicit `0`, `-` or `NC` means none); unreadable numbers are errors. Weekly hours are always L+T+P.
- **One-time ops for existing data (VIT, VWU):** `node scripts/audit-subject-duplicates.mjs` (read-only), resolve clashes, then `node scripts/backfill-subject-keys.mjs --college=<id> [--apply]`. Dashboard "Data check" (`GET /api/college/academics/overview?check=1`) re-checks consistency on demand.

### Student mentoring (HOD assigns, faculty mentors)

- **Model:** one mentor per student, stored on the student record (`mentorUid` = the mentor's LOGIN uid, plus `mentorName` / `mentorAssignedBy` / `mentorAssignedAt`; absent = none). Written ONLY by `POST /api/college/mentoring/assign` (HOD; every student must pass the HOD's department scope, `lib/mentoring/access.ts`; the mentor must be an available faculty member of the HOD's departments). Notes live at `students/{id}/mentoringNotes/{noteId}` (mentor + HOD only, never the student; delete = author only).
- **Read-only progress for the mentor** (`GET /api/college/mentoring/students/[id]?part=profile|attendance|results|internal`, PANEL_MEMBER/HOD; allowed for the student's mentor or the HOD who manages them): profile = the student's own roster detail groups (`buildOwnProfileGroups`); attendance = `computeStudentAttendanceHistory` per semester; results = PUBLISHED `semesterResults` with SGPA/CGPA/backlogs from `studentStanding` (`lib/mentoring/progress.ts`); internal marks = SUBMITTED `internalExamMarks` batches containing the student, resolved through the Exam Cell's `ExamConfiguration`.
- **Pages:** `/hod/mentoring` (Assign / Mentors / My Mentees) and `/panel/mentoring` (My Mentees), both opening `MenteeProgress`. Exited (RESIGNED/RETIRED) faculty are read-only, so they lose access automatically; the HOD reassigns their mentees. The HOD is always offered as a mentor for themselves (`isSelf`; `assign` lets them pick themselves even if their faculty record is filed outside their departments).
- **Mentoring Record (the college's "Student Mentoring Record" booklet)** - the default tab of `MenteeProgress` (`components/mentoring/record/*`), pages: Student information (booklet p.1 + 7.1), Previous record (7.2-8), one page per semester, Progress & placements (p.11), Activities & discipline (p.12), Mentor meetings (p.13-16). Read via `GET students/[id]?part=record|semesters|sheet&semester=n|entries`; written (mentor + HOD, same `authorizeMentoringStudent`) via `students/[id]/record/{profile,entries,entries/[entryId],semester}`.
  - **Page 1 / 7.1 are read from the student record** (`profileRecord.ts`); a value the student/Office holds is never overwritten here (409). Only a MISSING detail can be filled by the mentor, stored apart in `students/{id}/mentoringProfile/record.overrides` (keyed by roster key; the student's own value wins once it exists). Category is derived from the roster `caste`.
  - **Tables/lists are config-driven** (`recordSections.ts`: one definition = validation + form + table): rows live at `students/{id}/mentoringEntries/{id}` `{section, semester?, values}`. 7.2-7.5/8 are lists of dated items (added one at a time), not one textarea. Any row may be edited/removed by the current mentor/HOD (the record belongs to the student, not the author).
  - **Per-student semester subject copy** (`semesterSnapshot.ts`, `students/{id}/mentoringSemesters/{n}`): the curriculum (`subjectSemesterAssignments`) is ONE live set per department/year/semester edited in place, so reading it later shows an earlier batch the wrong subjects. The record keeps its own copy: refreshed from the live curriculum (filtered by the student's `regulation`) while the semester runs, FROZEN once it ends; a finished semester with no copy is rebuilt from the published results' subject snapshot, else from attendance. Capture happens when a semester page is opened - a semester nobody opened while it ran falls back to the results.
  - **Semester sheet** (`semesterSheet.ts`): attendance cumulative from the semester start up to Mid I / Mid II (earliest `examMidSchedules.fromDate` per course+semester, `semesterWindows.ts`) and end of semester; internal marks = the faculty's SUBMITTED batches (Exam Cell components, shown as entered - the Mid-I/Mid-II split of the paper form is not stored); grade/backlog/supplementary attempts, SGPA/CGPA from PUBLISHED `semesterResults` (`studentStanding`). Remarks per semester on the semester doc. Supplementary "mm-yy" is the month the sitting was imported.

### R&D records: edit before / after verification, and the change trail

- **Owners can edit at any status** (pending, with the coordinator, rejected, sent back, approved) in all 11 modules; Research Profiles and Citation Metrics are single-record-per-person, so a still-PENDING submission is overwritten in place (POST no longer 409s).
- **Editing an APPROVED record reopens it and records exactly what moved** (`src/lib/research/changeTracking.ts`): the first edit stores the verified content as `verifiedSnapshot`, and every edit stores `pendingChanges` = `{ changedAt, changedByName, changes: [{ key, label, before, after }] }` against that snapshot (never against the previous edit; putting a value back shows no change). Approval deletes both (`clearEditTrail`). Rejection / send-back keeps them, so a resubmission still shows the diff from the last verified version.
- **Shown** by `PendingChangesPanel` (record page `/r-and-d/record/[module]/[id]`, coordinator review dialog) and `ChangedFieldsButton` (every R&D pending-tab row); the reviewer notification lists the changed field names. A coordinator's correction recomputes `pendingChanges.changes`.
- Bookkeeping keys are excluded from the diff by `BOOKKEEPING` in that file; every other key a record holds is tracked, so a new form field needs no change there.

### Tenancy & roles (from `src/types/core.ts` — single source of truth)

- **Location-scoped roles** (`ADMINISTRATION`, `HR_ADMIN`, `ADMIN_OFFICE`, `LOCATION_DEPT_HEAD`) — profiles at `locations/{id}/locationUsers/{uid}`.
- **College-scoped roles** (`PRINCIPAL`, `VICE_PRINCIPAL`, `HOD`, `COLLEGE_OFFICE`, `PANEL_MEMBER`, `STUDENT`, internal-office roles, ...) — profiles at `colleges/{id}/users/{uid}`.
- **Global roles** (`SUPER_ADMIN`, `MANAGEMENT`, `FINANCE`, `PURCHASE_DEPT`) — profiles in `systemUsers/{uid}`.
- `COLLEGE_ADMIN`/`DIRECTOR` are normalized to `PRINCIPAL` at session time; `DEPARTMENT_OFFICE` normalized to `HOD` — real role preserved in `realRole`.
- `ROLE_LEVEL` (0–6) + `ROLE_SCOPE` drive coarse page gating in `proxy.ts` and role inheritance (`rolesInheritedBy`, `canRoleAccessRole`). Real data isolation happens **per API route** via `verifySession.ts` + `lib/departments/scope.ts`.

### Auth flow

1. Client Firebase Auth → `POST /api/auth/session` verifies the ID token, resolves role/collegeId/locationId, sets signed (HMAC-SHA256, Web Crypto) httpOnly `fms-session` cookie (24h).
2. `src/proxy.ts` gates dashboard **pages** only.
3. Every API route guards itself through `src/lib/auth/verifySession.ts`. Bearer-token routes (cron, public APIs) use `verifyFirebaseToken.ts`.
4. Firestore security rules (`firestore.rules`) are a second, coarser layer: they see only `{role, collegeId, locationId}` claims and **cannot** distinguish seat-holders or normalized roles.

## Coding Conventions & Guardrails

### Style

- Path alias `@/*` → `src/*` (mirrored in `vitest.config.mts`). Import from `@/types` barrel, `@/lib/...`, `@/components/...`.
- API routes: named exports `export async function GET/POST/PATCH/DELETE`, `export const dynamic = "force-dynamic"` when reads must not be cached; dynamic segments receive `{ params }: { params: Promise<{ id: string }> }` (Next.js 16 — params are async).
- Error handling pattern per route: `try { ... } catch (err)` → re-check sentinel errors thrown by guards (`UNAUTHORIZED`, `NO_COLLEGE_CONTEXT`) → 401; validation failures → `NextResponse.json({ error }, { status: 400 })`; optimistic-concurrency misses → **409**; everything else → `console.error("[route-name]", err)` + 500. Never leak internals.
- Server-side Firebase **always** via `getAdminDb()`/`getAdminAuth()`/`getAdminStorage()` from `@/lib/firebase/admin` — never the client SDK in API routes. Multi-doc writes use `db.runTransaction` or `ChunkedBatch` (`lib/firestore/chunkedBatch.ts`) — Firestore caps batches at 500.
- All date-of-record logic in attendance goes through `lib/attendance/istTime.ts` (`istDateKey`, `istMidnightUTC`, `getISTParts`) — never ambient `Date` getters; all colleges are IST (`Asia/Kolkata`).
- Types live in `src/types/*.ts` (one file per domain); types import `Timestamp` from `firebase/firestore`. Cross-cutting events extend the `AuditLog` and `AppNotification` unions in `core.ts`.
- Notifications via `lib/notify.ts` (`notify`, `notifyRole`) — not hand-rolled per route. UI toasts via `useToast()`; auth via `useAuth()` + Zustand `authStore`.
- Naming: `camelCase` files in lib, `PascalCase.tsx` components, route folders kebab-case. Zod for request validation in newer routes.

### Strict boundaries — do NOT modify without permission

1. **`src/lib/auth/verifySession.ts`** — imported by ~279 of 290 API route files. `requireRole` deliberately *rewrites* roles (HOD-seat resolution); changing resolution order changes ~420 `role === "HOD"` checks.
